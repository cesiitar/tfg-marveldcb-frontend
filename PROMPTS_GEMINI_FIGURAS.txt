--------------------------------------------------------------------------------
Genera una imagen PNG que imite EXACTAMENTE este estilo de diagrama de flujo

ESTILO VISUAL OBLIGATORIO:
- Fondo blanco.
- Cajas: rectángulos con bordes LIGERAMENTE redondeados (esquinas suaves, no

CONTENIDO Y POSICIÓN (respetar al pie de la letra):

FILA SUPERIOR (entrenamiento), de izquierda a derecha, alineada horizontalmente:
1. Caja NARANJA, texto línea 1: "Base de Datos", línea 2: "(Partidas)".

3. Caja AZUL CLARO, texto línea 1: "Extracción de", línea 2: "Features".
4. Flecha horizontal negra hacia la derecha.
5. Caja AZUL CLARO, texto línea 1: "Entrenamiento", línea 2: "SVM".
6. Flecha horizontal negra hacia la derecha.
7. Caja NARANJA, texto línea 1: "Modelo", línea 2: "(.pkl)".

   lado), que llega hasta la caja "Inferencia (Predicción)" de la fila inferior.

FILA INFERIOR (recomendación), de izquierda a derecha, paralela a la superior

5. Caja NARANJA, texto línea 1: "Mazos", línea 2: "Recomendados".

OPCIONAL (si hay espacio): Al pie de la imagen, en una línea centrada y fuente

Salida: una sola imagen PNG, proporciones adecuadas para ancho de página (~75%
de A4), estilo plano y profesional, sin decoraciones adicionales.

3. DIAGRAMA UML – CLASES (diagrama_uml_clases.png)
--------------------------------------------------------------------------------
Genera un diagrama UML de clases para un documento de diseño de software (TFG).
Debe incluir las siguientes clases y relaciones:

- User: id, auth0_id, email, name, picture_url, created_at, updated_at.
- Card: id, name, aspect, type, cost, pack_code, deck_limit, is_unique,
  marvelcdb_code (y otros atributos opcionales).
- CardSet: id, name, code, card_count.
- Deck: id, name, description, hero_name, hero_id, aspect, cards (JSON),
  is_public, user_id (FK), created_at, updated_at.
- GameConfiguration: id, user_id (FK), deck_id (FK), difficulty, villain_id
  (FK), result, played_at.
- UserFavorite: id, user_id (FK), deck_id (FK), created_at.
- DeckComment: id, deck_id (FK), auth0_id, comment_text, created_at, updated_at.

Relaciones:
- User 1 --- * Deck (un usuario tiene muchos mazos).
- User 1 --- * GameConfiguration (un usuario muchas partidas).
- User * --- * Deck (favoritos) a través de UserFavorite.
- Deck 1 --- * GameConfiguration (un mazo en muchas partidas).
- Deck 1 --- * DeckComment (un mazo muchos comentarios).
- Card: referenciada por GameConfiguration (villain_id), Deck (hero_id y en
  lista de cartas).

Estilo: notación UML estándar (cajas con nombre de clase, compartimento de
atributos, flechas con cardinalidad 1, *, etc.). Trazos claros, texto legible.
Puedes simplificar si hay muchas clases (por ejemplo solo las 5 principales:
User, Card, Deck, GameConfiguration, UserFavorite) y el resto mencionarlas o
añadir una nota. Formato para caber en una página (~ancho A4).

3b. DIAGRAMA UML – CASOS DE USO (diagrama_uml_casos_uso.png)  [PARA DISEÑO]
--------------------------------------------------------------------------------
Genera un diagrama UML de casos de uso para un documento de diseño (TFG).
Sistema: plataforma web AIForge de gestión de mazos de Marvel Champions (crear
mazos, importar desde MarvelCDB, registrar partidas, recomendación IA).

Actor principal: "Usuario" (o "Jugador"), representado con el icono de actor
(palito con círculo) a la izquierda del sistema.

Casos de uso (elipses o burbujas dentro del rectángulo del sistema), con nombres
claros y en español. Esquematizar en estos tres paquetes o áreas:

Área "Búsqueda y catálogo":
- Explorar cartas y mazos (único caso de uso en este apartado).

Área "Partidas y recomendación":
- Registrar partida (con mazo, villano, dificultad, resultado).
- Ver historial de partidas.
- Eliminar tus propias partidas.
- Obtener recomendación de mazos (IA / SVM) según villano y dificultad.

Área "Gestión de mazo":
- Crear mazo (manual o importar desde MarvelCDB).
- Importar mazo desde MarvelCDB.
- Editar mazo (propio).
- Eliminar mazo (propio).
- Marcar / desmarcar mazo como favorito.
- Comentar mazo / eliminar comentario (último caso de este apartado).

Fuera de áreas (bloque común): Iniciar sesión / Registrarse, Ver perfil (si está
autenticado), Contactar con soporte (consultar ayuda o soporte de la plataforma).

El rectángulo del sistema debe llamarse "AIForge". Las líneas entre el actor y
cada caso de uso (asociación). Dibujar los tres paquetes (Búsqueda y catálogo,
Partidas y recomendación, Gestión de mazo) de forma visible en el diagrama.

Estilo: notación UML de casos de uso estándar. Texto legible. Adecuado para
ancho de página (puede ser algo más ancho que A4 si hay muchos casos).
DESTINO: Capítulo de DISEÑO (junto al diagrama de clases).

4. DIAGRAMA DE SECUENCIA – REGISTRAR PARTIDA (secuencia_registrar_partida.png)
   [PARA IMPLEMENTACIÓN]
--------------------------------------------------------------------------------
Genera un diagrama UML de secuencia para un documento de diseño (TFG). Título o
contexto: "Registrar partida".

Participantes (líneas de vida), de izquierda a derecha:
- Usuario
- Frontend (navegador)
- Backend API (FastAPI)
- Base de datos (SQLite)

Mensajes en orden cronológico (flechas con etiquetas):
1. Usuario selecciona mazo, villano, dificultad y resultado en el frontend.
2. Usuario pulsa "Guardar" o "Registrar partida".
3. Frontend envía petición POST (o similar) al Backend con los datos y cabecera
   X-Auth0-ID (usuario autenticado).
4. Backend valida datos y escribe en la base de datos (INSERT en
   game_configurations).
5. Base de datos confirma.
6. Backend responde éxito al Frontend.
7. Frontend muestra confirmación al Usuario (toast o mensaje).

Estilo: diagrama de secuencia UML estándar (cajas en la parte superior para cada
participante, líneas de vida punteadas verticales, flechas horizontales con
mensajes). Texto legible. Adecuado para ancho de página (~90% A4).

5. DIAGRAMA DE SECUENCIA – RECOMENDACIÓN IA (secuencia_recomendacion_ia.png)
   [PARA IMPLEMENTACIÓN]
--------------------------------------------------------------------------------
Genera un diagrama UML de secuencia para un documento de diseño (TFG). Título o
contexto: "Obtener recomendación de mazos por IA (SVM)".

Participantes (líneas de vida), de izquierda a derecha:
- Usuario
- Frontend (navegador)
- Backend API (FastAPI)
- Módulo IA / Modelo SVM
- Base de datos (SQLite) [opcional, si el modelo se carga desde disco]
- Modelo (.pkl) [opcional, como recurso]

Mensajes en orden cronológico:
1. Usuario selecciona villano y dificultad en el frontend y pide recomendación.
2. Frontend envía petición al Backend (por ejemplo GET o POST con villano y
   dificultad), con X-Auth0-ID si aplica.
3. Backend recibe la petición y solicita al Módulo IA la predicción o
   recomendación.
4. Módulo IA carga el modelo entrenado (desde archivo .pkl en disco, si se quiere
   detallar).
5. Módulo IA evalúa combinaciones héroe–aspecto según probabilidad de victoria
   (usando datos de partidas que pueden venir de BD o del modelo ya entrenado).
6. Módulo IA devuelve al Backend la lista de mazos recomendados (o
   combinaciones ordenadas).
7. Backend genera o recupera los mazos completos (puede consultar BD para
   cartas) y responde al Frontend.
8. Frontend muestra los mazos recomendados al Usuario.

Si no hay modelo entrenado (pocos datos): Backend usa criterio de respaldo y
devuelve recomendaciones deterministas (puedes añadir una nota o rama alt en
el diagrama).

Estilo: diagrama de secuencia UML estándar. Texto legible. Adecuado para ancho
de página (~90% A4). Este diagrama debe reflejar que el SVM es el núcleo del
flujo de recomendación.
